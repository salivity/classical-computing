How Does Strict 2PL Prevent Dirty Reads and Lost Updates?

Strict Two-Phase Locking is a concurrency control protocol used in classical database management systems to ensure serializability and recoverability among concurrent transactions. By requiring transactions to acquire all necessary locks before releasing any of them and holding exclusive locks until the transaction commits or aborts, Strict Two-Phase Locking eliminates anomalies such as dirty reads and lost updates.

Understanding Strict Two-Phase Locking

In classical computing, databases rely on locks to coordinate access to shared data items among concurrent transactions. Two-Phase Locking (2PL) divides a transaction's execution into two distinct phases:

  1. Growing Phase: A transaction may acquire locks on data items, such as shared (\(S\)) locks for reading and exclusive (\(X\)) locks for writing, but it cannot release any locks.
  2. Shrinking Phase: A transaction releases its locks and cannot acquire any new locks.

Strict Two-Phase Locking (Strict 2PL) adds a critical constraint to the shrinking phase: all exclusive (\(X\)) locks held by a transaction must be retained until the transaction either commits or aborts. This guarantees that no other transaction can observe or overwrite uncommitted changes.

How Strict 2PL Prevents Dirty Reads

A dirty read occurs when a transaction \(T_2\) reads a data item that has been modified by another transaction \(T_1\) before \(T_1\) has committed. If \(T_1\) subsequently aborts and rolls back its changes, \(T_2\) will have operated on invalid, non-existent data.

Strict 2PL prevents dirty reads through the following mechanism:

  • When \(T_1\) intends to write to a data item \(A\), it must first acquire an exclusive lock \(X(A)\).
  • Under Strict 2PL, \(T_1\) holds \(X(A)\) until it reaches its commit or abort point.
  • If \(T_2\) attempts to read \(A\), it must request a shared lock \(S(A)\).
  • Because \(X(A)\) and \(S(A)\) are incompatible, \(T_2\) is blocked and forced to wait until \(T_1\) finishes and releases \(X(A)\).

By the time \(T_2\) is granted \(S(A)\), \(T_1\) has either committed its changes (making the data valid) or aborted and rolled them back (restoring the previous valid state). Consequently, \(T_2\) can never read uncommitted data.

How Strict 2PL Prevents Lost Updates

A lost update occurs when two concurrent transactions, \(T_1\) and \(T_2\), both read the same data item \(A\) and then update it based on the value they read. Because both transactions overwrite \(A\) without knowing about the other's modification, the first update is lost.

Strict 2PL prevents lost updates by serializing write access to the data item:

  • If \(T_1\) acquires \(X(A)\) to update \(A\), \(T_2\) cannot acquire \(X(A)\) until \(T_1\) commits or aborts.
  • Even if \(T_1\) and \(T_2\) both initially acquire shared locks \(S(A)\) to read \(A\), neither can upgrade to an exclusive lock \(X(A)\) while the other still holds \(S(A)\).

In the lock-upgrade scenario, if both transactions attempt to upgrade \(S(A)\) to \(X(A)\) simultaneously, a deadlock occurs. The database management system detects this deadlock and aborts one of the transactions, allowing the other to proceed safely. In all cases, one transaction completes its update before the other can begin modifying \(A\), ensuring that no update is ever overwritten.

Trade-offs of Strict 2PL

While Strict 2PL effectively guarantees conflict serializability and strict recoverability, it introduces a few operational trade-offs:

  • Reduced Concurrency: Holding exclusive locks until the end of a transaction increases lock contention and wait times for other transactions.
  • Deadlocks: Because transactions wait on locks held by others, circular wait conditions can arise, requiring deadlock detection or prevention mechanisms.

Despite these costs, Strict 2PL remains a foundational protocol in classical relational database systems due to its reliability in maintaining data integrity.
