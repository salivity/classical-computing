How Does the Call Stack Manage Subroutine Calls?

The call stack is a Last-In, First-Out memory structure that tracks active subroutines in a program. Whenever a function is called, the system pushes a new activation record onto the stack to store its return address, local variables, and saved registers. When the subroutine finishes, that record is popped off, allowing execution to resume seamlessly at the exact point where the caller left off.

The Role of Activation Records

An activation record, commonly called a stack frame, is a contiguous block of memory allocated on the call stack for a single execution of a subroutine. Because subroutines can call other subroutines—or even themselves recursively—each active invocation needs its own isolated workspace so that data from one call does not overwrite another.

A typical stack frame contains:

  • Return address: The memory address of the instruction immediately following the call site in the caller.
  • Saved frame pointer: The base address of the caller's stack frame, allowing the stack to be restored upon return.
  • Local variables: Variables declared inside the subroutine whose lifetimes are bound to that specific call.
  • Parameters and saved registers: Arguments passed to the function (if not passed in CPU registers) and any caller registers that the subroutine must preserve.

Saving and Restoring Return Addresses

Before jumping to a subroutine, the CPU must remember where to return once the subroutine completes. In architectures like x86, the CALL instruction automatically pushes the current instruction pointer (the address of the next instruction) onto the stack before jumping to the target function's address. In RISC architectures such as ARM or MIPS, the return address is first placed into a dedicated link register, and the subroutine pushes that register onto the stack if it intends to call another function.

When the subroutine reaches its RET (return) instruction, the CPU pops the return address from the top of the stack and loads it back into the instruction pointer. Execution then continues in the caller as if the subroutine call were a single, uninterrupted step.

Managing Local Variables and Pointers

Two CPU registers coordinate access to the current stack frame:

  • Stack Pointer (\(SP\)): Always points to the current top of the stack. On most architectures, the stack grows downward toward lower memory addresses, so allocating space means subtracting from \(SP\).
  • Frame Pointer (\(FP\) or Base Pointer, \(BP\)): Points to a fixed reference location within the current stack frame.

While \(SP\) moves as data is pushed and popped during a function's execution, \(FP\) remains constant for the duration of the call. This stability allows the compiler to reference local variables and parameters using fixed offsets relative to \(FP\) (for example, \(FP - 4\) for the first local integer, or \(FP + 8\) for a parameter).

The Call and Return Lifecycle

A standard subroutine call follows a predictable sequence known as the prologue and epilogue:

  1. Call: The caller pushes arguments (if needed) and executes a call instruction, pushing the return address.
  2. Prologue: The callee pushes the caller's \(FP\) onto the stack, sets \(FP\) to the current \(SP\), and subtracts the total size of its local variables from \(SP\) to reserve space.
  3. Execution: The subroutine runs, reading and writing local variables via fixed offsets from \(FP\).
  4. Epilogue: The callee sets \(SP\) back to \(FP\) (instantly deallocating all local variables), pops the saved \(FP\) to restore the caller's frame, and executes a return instruction to pop the return address.

Stack Limits and Overflow

Because the call stack occupies a fixed, finite region of memory, deeply nested calls or unbounded recursion can exhaust the available space. When \(SP\) moves past the allocated boundary of the stack, a stack overflow occurs, typically causing the operating system to terminate the program with a fault. Proper base cases in recursive functions and avoiding excessively large stack-allocated arrays help keep stack usage within safe bounds.
