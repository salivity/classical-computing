Why Does Polling Use More CPU Cycles Than Interrupts?

Polling consumes excessive processor cycles because it forces the central processing unit to repeatedly check the status of an input or output device in a tight loop, even when no data is ready. In contrast, interrupt-driven I/O allows the processor to execute other useful instructions or enter a low-power state until the hardware explicitly signals that it requires attention. This fundamental difference in how waiting time is managed determines overall system efficiency, responsiveness, and energy consumption.

How Polling Works

In a polling-based system, the CPU takes an active role in monitoring peripheral devices such as keyboards, network cards, or storage controllers. The processor executes a loop—often called a busy-wait loop—that continuously reads a status register on the device.

while ((device_status_register & READY_BIT) == 0) {
    // Do nothing; keep checking
}
process_data(device_data_register);

Every iteration of this loop consumes instruction cycles, memory bus bandwidth, and power. If a device takes \(10\text{ ms}\) to respond and a processor operates at \(3\text{ GHz}\), the CPU can waste tens of millions of cycles just asking whether the device is ready:

\[\text{Wasted Cycles} = f_{\text{CPU}} \times t_{\text{wait}} = (3 \times 10^9\text{ Hz}) \times (10 \times 10^{-3}\text{ s}) = 3 \times 10^7\text{ cycles}\]

During this entire waiting period, the CPU cannot perform meaningful computation for other tasks unless the operating system preempts the thread, which still incurs scheduling overhead.

How Interrupt-Driven I/O Works

Interrupt-driven I/O reverses this relationship by shifting the responsibility of notification from the CPU to the hardware device. When the processor initiates an I/O operation, it does not wait for completion. Instead, it immediately moves on to execute other programs or enters an idle sleep state.

When the peripheral finishes its task—such as receiving a network packet or completing a disk read—it asserts an electrical signal on an interrupt request (IRQ) line connected to the interrupt controller. The controller then notifies the CPU, which pauses its current execution, saves its state, runs a brief Interrupt Service Routine (ISR) to handle the data, and resumes its previous work.

Key Reasons Polling Wastes More Cycles

1. Continuous Busy-Waiting

Polling ties up the execution pipeline with status-check instructions. Even if a device is idle \(99\%\) of the time, the CPU spends its cycles repeatedly reading the same unchanged register.

2. Poor Scalability with Multiple Devices

If a system must monitor \(N\) devices via polling, the CPU must cycle through all \(N\) status registers sequentially. As \(N\) grows, the time spent checking idle devices increases linearly, reducing the time available for actual application logic. Interrupts scale much better because idle devices generate zero CPU overhead.

3. Inability to Enter Low-Power States

Modern processors save energy by entering deep sleep states (such as C-states) when no work is available. Because polling keeps the CPU actively executing instructions in a loop, the processor cannot enter these low-power states, leading to higher power draw and thermal output.

When Polling Is Still Used

Despite its cycle overhead, polling is not obsolete. In high-throughput, low-latency environments—such as high-speed network interfaces handling millions of packets per second—interrupts can become a bottleneck due to the overhead of context switching and saving CPU state on every event. In these scenarios, hybrid approaches like NAPI (New API) in the Linux kernel use interrupts when traffic is low and switch to polling during heavy bursts to maximize throughput.
